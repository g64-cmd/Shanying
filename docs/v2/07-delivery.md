# 07 · 三分支协作、里程碑与验收

## 1. 仓库与分支

采用一个仓库承载三端，main 始终包含所有已集成代码。

| 分支 | 主要负责 | 共享变更规则 |
| --- | --- | --- |
| `dev/backend` | server、migrations、服务部署、服务测试 | 提交 contracts 变更并生成三端样例 |
| `dev/web` | apps/web、packages/api-client-web | 不自行改变业务状态和接口语义 |
| `dev/android` | apps/android | 不为追赶后端私自重写公共 DTO |

这三个分支可反复使用，但不能几个月不合并。每完成一个1—3天的小切片就集成回 main，随后三个分支都合入最新 main；长于一周的未集成工作应拆小。main 接受实现增量，未完成功能由 feature flag 隔离，不能等四条主线全部做完才首次集成。

顺序：设计基线提交/评审 → 共同仓库基底提交 → 从同一 main 提交建立三个分支 → P0公共契约先合入main → 三端同步 → 每个业务切片分别提交小PR。2026-10-10 的共同基底与本地分支初始化见[开发入口](../development.md)；P0 探针和后续 PR 尚未完成。

推荐对这三个反复使用的分支使用普通 merge commit，保留共同祖先；已共享分支不 rebase/force push。若选择 squash，则合并后从新main重建该分支，不能混用历史策略。契约变更先合并再让客户端同步，不在三个分支各自手抄一份。

示意（后续集成流程，尚未执行业务增量）：

```text
main:            A -- D -- C -- B1 -- W1 -- A1 -- B2 ...
                      |    |     |     |     |
dev/backend:        同一基线 → 小切片 → PR → 同步main
dev/web:            同一基线 → mock/页面 → PR → 同步main
dev/android:        同一基线 → mock/页面 → PR → 同步main

D = 文档基线，C = 公共契约，B/W/A = 各端增量
```

同一目录不能同时切换三个分支。未来需要三路同时工作时使用独立 Git worktree；一个人顺序开发可只开当前分支。契约、根锁文件和公共部署配置指定一位当前维护者，减少并发编辑冲突。

## 2. 开发次序与里程碑

完整范围较大，推荐先得到可演示的视频系统，再叠加推荐与聊天。三个分支是责任边界，不表示单人需要同时推进三个大任务。

| 阶段 | 交付物 | 硬验收门槛 | 估算专注工时 |
| --- | --- | --- | --- |
| P0 基线与技术验证 | 三端最小工程、锁文件、Compose、契约生成、CI、六项选型探针 | 空目录按文档启动；Web/Android读取相同mock；工具链可重现；Gorse禁训练验证 | 25—40 h |
| P1 第一条真实链路 | 认证、上传、转码、审核、视频详情；Web为完整链路，Android登录和播放 | 真实上传→处理→审核→两端播放；失败/重试可观察 | 60—100 h |
| P2 视频与搜索 | 三种Feed基础、点赞评论关注收藏、个人页、中文搜索、管理下架 | 权限、并发关系操作、分页、下架与索引重建测试通过 | 80—130 h |
| P3 推荐 | 行为、Gorse标签候选、混排、冷启动、降级、评估报告 | 无训练任务；固定数据可重放；与latest/hot比较并公布不足 | 80—120 h |
| P4 聊天与客户端补齐 | 单聊、卡片、读游标、断线/多设备；Android发布与弱网完善 | ACK前断电重发不重复；Pub/Sub中断可补偿；双端实测 | 80—130 h |
| P5 展示交付 | 压测、恢复演练、部署、演示数据/录像、最终文档 | 另一台机器复现；记录环境/提交/失败项；恢复演练完成 | 60—100 h |

合计 **385—620 h**，是架构拆分后的粗估，不是承诺；每周15—20h约20—42周，技能熟悉程度、UI深度和真机问题会显著改变结果。每阶段结束用实际耗时修订后续估算。P0—P3（约245—390h）可形成第一版有证据的简历项目，不必等聊天与最终交付都完成才展示。电商不计入该工时或 v2 验收。

若需要更早展示，先以P1—P2作为演示里程碑；完整v2仍保留P3—P5，不将后续计划写成已完成能力。

## 4. 测试策略与CI

| 层次 | 核心内容 | 运行时点 |
| --- | --- | --- |
| 静态/构建 | Go格式与lint、TS strict、Android lint、依赖边界 | 相关路径PR |
| 领域单测 | 发布、媒体处理状态机；排序配额；游标校验 | 每个PR |
| PG集成 | 唯一键、事务回滚、消息计数锁、outbox、消息序号 | 后端/迁移PR；真实PG容器 |
| 契约 | OpenAPI合法性与breaking diff、生成无差异、JSON正反例 | contracts变更触发三端全矩阵 |
| 客户端 | Query竞态、令牌刷新、播放器清理、Room迁移、离线队列 | 相应客户端PR |
| 端到端 | 两账号上传/评论/搜索/聊天的真实闭环 | 合入main及阶段验收 |
| 故障/负载 | 组件停机、worker终止、并发发消息、长连接恢复 | 相关阶段完成后，发布前 |

GitHub Actions路径过滤负责减少工作量，但根依赖、契约、生成器、CI文件变化必须扩展到相关矩阵。后端任务固定 `runs-on: ubuntu-24.04`，server 构建、运行、真实 PG 集成及阶段验收在 Ubuntu 24.04 完成；Windows/WSL 不作为 server 运行环境。Android单元测试/构建在普通runner，关键Espresso流程在模拟器；阶段验收补一台真机，不拿APK能构建替代播放体验。

PR完成定义：契约与实现一致、关键失败路径有测试、无未解释的生成差异、迁移可在旧数据上执行、文档和配置示例已更新。发布/消息等核心状态变更必须有可复现的集成测试，不用“覆盖率100%”替代业务不变量。

## 5. 性能与恢复验收计划

以下均为**目标，不是已有成绩**。P1先测基线，P5在固定环境记录真实结果，不达标则报告差距。

保留当前文档的基准环境规划：4 vCPU/2 GB本地测试机（实际服务器规格待P0核实），负载发生器独立；数据集1万账号、10万条视频元数据、100万条行为，100段可复现生成的有效视频样片。大量元数据用于查询压力，不声称有10万个真实可播放视频。先在2 GB内存约束下测量组件组合和数据规模，未能稳定承载时先报告容量上限，下面目标不视为已证明可达。合成行为指标只证明流程和模拟场景表现，不能外推真实用户偏好或商业收益。

| 场景 | 初始目标 | 如何测量 |
| --- | --- | --- |
| Feed元数据 | 100 RPS，p95≤300 ms，非预期5xx<1% | k6开放到达模型；记录冷/热缓存和降级比率 |
| 中文搜索 | 30 RPS，p95≤500 ms；索引延迟p95≤10 s | 固定查询集；检索相关性与性能分别报告 |
| 聊天 | 200连接、20消息/s，持久ACK p95≤200 ms | 测ACK和接收端延迟两种指标，包含补拉修复 |
| 首帧 | 固定设备/20 Mbps带宽/50 ms RTT，p95≤2 s | 冷/热缓存各至少100次播放，记录编码和清晰度 |
| 媒体处理 | 成功/失败与资源消耗可解释 | 同样片集报告转码耗时比，不承诺固定倍速 |
| 故障恢复 | ACK后消息不丢、重复发布不产生重复视频、worker可恢复 | 注入指定故障窗口，保存日志和最终数据库断言 |
| 备份恢复 | 演示环境RPO≤24 h，RTO≤2 h | 另起空环境恢复PG和媒体，抽样播放/消息核验 |

HTTP负载每组预热2 min、测量10 min、至少3次独立重复；保存提交SHA、镜像、配置、硬件、数据种子、脚本、原始结果、p50/p95/p99、CPU/RSS/IO与错误。视频字节流和API容量分开测，不把“100 RPS元数据”说成“100路视频分发”。

## 6. 运维与异常场景

必须有健康检查与就绪检查分离：api进程活着不等于PG可写。推荐/搜索故障可局部降级，不应导致所有登录/消息接口一起被判不就绪。优雅关闭先停止接新任务，再限时排空；未完成job依靠lease恢复。

数据库迁移采用扩展→兼容读写→回填→收缩；破坏性drop不与应用切换同一步。发布保留上个镜像，新旧版本与当前schema兼容后才能回滚；不能把强行执行down迁移作为默认恢复手段。

保留安全的开发种子，账号/行为/视频均明确为演示数据。日志不含密码、token、完整地址或聊天正文。配置从环境注入，测试凭证不用于线上。对上传、聊天、搜索、登录分别限制请求规模和速率。

## 7. 简历证据包

每个阶段保留：对应提交/tag、演示步骤、真实测试结果、架构ADR、已知限制、可复现实验。最有价值的三条叙事是：

1. 从横向分层重构为具有业务所有权的模块化单体，用契约连接React与Java Android。
2. 在上传/索引/聊天中实现并验证幂等、事务outbox、状态机和故障恢复。
3. 集成完全不训练的推荐链路，固定数据比较排序效果、延迟、冷启动和失败降级。

简历中的QPS、延迟改善、推荐提升和用户规模只能来自保留的实测。当前阶段只能写“完成架构设计/选型”，不能写“已构建高并发分布式短视频平台”。
