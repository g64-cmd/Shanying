# 闪映 v2 · 设计评审稿

日期：2026-10-09（北京时间）  
状态：0.2 版设计已获项目负责人接受，作为后续实施基线。开发约束见仓库根目录 [AGENTS.md](../../AGENTS.md)。

## 1. 建议结论

采用 **Monorepo + 按业务划分的模块化单体 + 独立 worker + 契约优先的双客户端**。

Go + Hertz 负责业务、事务、权限和异步任务；React + TypeScript 负责 Web；Java + Android Views 负责 Android。数据库使用 PostgreSQL，Redis 保存可重建的缓存。视频交给对象存储和 FFmpeg，搜索交给 Meilisearch。推荐使用 Gorse 标签相似召回，关闭全部模型训练，Go 完成业务混排和降级。

扩展性的核心是：**每份业务数据只有一个拥有者，模块通过小接口或持久化事件协作，复杂流程有状态机、幂等和失败恢复。** 不以服务数量或中间件数量衡量设计水平。

完整 v2 覆盖视频、搜索、推荐、聊天四条主线，但限定为个人可维护的作品规模；这是参考抖音主要交互的短视频平台，并非复刻其生产能力，也不声称采用抖音内部架构。

## 3. v2 的交付边界

| 主线 | 完整 v2 必须完成 | 后续扩展，不计入 v2 验收 |
| --- | --- | --- |
| 基础视频 | 账号、资料、关注、上传、转码、封面、推荐/最新/关注流、点赞收藏、两级评论、举报下架 | 直播、剪辑器、美颜、音乐版权库、多区域分发 |
| 搜索 | 中文标题/描述/标签搜索、筛选、结果分页、下架过滤、索引重建 | 多模态搜索、复杂查询 DSL、搜索广告 |
| 推荐 | 行为采集、标签相似召回、热度/新内容/关注混排、冷启动、去重、实验标识和离线评估 | MF/FM/深度模型训练、微调、实时特征平台、自动调参 |
| 电商扩展 | 仅记录数据归属、依赖方向和协议演进边界，不实现电商 | 商品、购物车、订单、库存、支付、商家后台等全部电商功能 |
| 聊天 | 一对一文本、视频卡片、历史消息、已读游标、多设备同步、断线补拉、拉黑 | 商品卡片、群聊、音视频通话、端到端加密、可靠后台推送 |
| 管理 | Web 管理页面：审核、下架、举报处理、任务重试、操作审计 | Android 管理端、自动内容识别模型 |

账号、权限、管理入口和通知是四条主线的配套能力。Android 实现用户浏览、发布、聊天；管理员操作集中在 Web。

## 5. 已接受的主要决定

| 编号 | 本稿默认 | 改变它会影响什么 |
| --- | --- | --- |
| D01 | 模块化单体，不在起步时拆微服务 | 开发和运维成本、事务复杂度 |
| D02 | Hertz + pgx/sqlc | Go 学习成本、类型安全、代码生成 |
| D03 | Meilisearch 独立搜索 | 中文检索能力与一个新增依赖的成本 |
| D04 | Gorse 非训练模式，显式关闭 MF/FM | 推荐交付边界、运行配置验证 |
| D05 | S3 接口 + SeaweedFS 本地对象存储 | 替代旧 MinIO 的兼容性验证 |
| D06 | v2 暂不实现电商，保留扩展边界；聊天先做单聊 | 完整 v2 的体量和完成概率 |
| D07 | 三个短周期开发分支，持续合入 main | 合并成本、跨端接口同步 |
| D08 | Web 先跑通一个闭环，Android 随契约跟进 | 单人开发顺序和展示时点 |

本轮依据是两个旧仓库的固定提交源码和官方文档；未运行旧项目，也没有 v2 性能数据。本文所有时延、容量、工期均是待验证目标或估算。
