# Design

## Context

仓库当前只有规划及检查脚本，无 Go 应用、迁移或客户端实现。define-shanying-platform 为总需求路线，本 change 只细化后端底座及账号权限；总路线任务保持未完成。旧历史中的 Java/微服务/电商排除均不适用。

## Goals / Non-Goals

Goals：编码前完成单一契约、可实施的数据约束、线性化状态转换与负向/并发测试矩阵；单机运行、Docker 优先，三端提前验证 API。

Non-Goals：本轮编码、执行数据库迁移、搭建完整客户端 UI；视频、消息、商家/管理员界面、订单资金表、头像上传、注销/邮箱更换、OAuth/MFA。未来模块仅定义事实接口与联合设计门槛，不建空泛 RBAC 或分布式框架。

## Decisions

### 1. 可直接评审的设计入口

- [工程结构与规则](../../../docs/backend/engineering.md)：包边界、依赖方向、Hertz适配、pgx事务、配置、日志、安全参数及联合设计门槛。
- [唯一 OpenAPI](../../../contracts/openapi.yaml) 与 [API说明](../../../docs/api/account-access.md)：28个操作、精确请求响应、Web/Android凭据及失败恢复。
- [数据库](../../../docs/backend/account-database.md)：10张业务/基础表、约束、索引、锁顺序及迁移计划。
- [状态转换](../../../docs/backend/account-state-machines.md)：邮箱凭证、会话、关系、隐私及授权优先级。
- [测试矩阵](../../../docs/backend/account-test-matrix.md)：带编号场景当前全部not_run，涵盖纯逻辑、真实PG、HTTP和客户端。

这些文档是本 change 的设计组成部分；冲突时不得自行选一份实现，先统一契约、状态及测试。

### 2. 单机与工程复杂度

单 Go 服务、Hertz HTTP、pgx/v5 参数SQL、PostgreSQL17 和同进程有界邮件任务；不使用 JWT 自包含权限、Redis、ORM、RPC、消息集群。数据库可即时撤销opaque会话，符合当前单机规模；代价是每次授权需数据库，不以缓存旧权限降级。

### 3. 注册及密码

先邮件验证，再提交密码建账号，避免未验证者预占账号密码。重复/存在邮箱请求响应一致、邮箱HMAC限流、Argon2id哈希。链接由前端fragment接收并POST消费，邮件扫描器GET不改状态。SMTP任务和凭证同事务持久，SMTP网络在事务外，允许重复邮件而不重复消费。

### 4. 跨端会话

Web同源HttpOnly/Secure cookie + Origin和CSRF自定义头；Android响应体tokens + Bearer访问。随机32-byte token只存SHA256，不把角色权限放进可长期缓存的JWT。access15min、idle7d、absolute30d；刷新轮换，旧refresh重放撤销该设备session。客户端single-flight，刷新响应丢失重新登录；相比保存可解密的重试响应，选择更少秘密持久化和明确失败恢复。

### 5. 关系线性化

关系写锁双方用户行，事务内复核隐私和block；拉黑原子删除双向accepted/pending，解黑不恢复。这是2026-10-26用户确认的产品选择。隐私改动使用version，私密转公开保留pending为本切片保守默认，不隐式审批。批准引用申请ID避免旧请求作用于新申请。将来消息/作品用相同关系事实但在自己的事务内授权。

### 6. 权限与未来业务

首版只有成员身份和对象归属授权，不通过客户端role获得商家/平台权限。数据模型保留stable user ID和RESTRICT外键，不提供级联硬删；后续资金设计仍需自己的快照与账务验证。已拉黑用户的公开账号资源在有身份请求中不可访问；不能承诺识别其退出登录后的匿名访问，这不是防止公开资料被任何人看到的机制。

## Risks / Trade-offs

- 刷新重放策略使偶发丢包需要重登 → 明确协议，跨标签single-flight，专项客户端恢复测试。
- 用户行锁降低热点并发 → 首版换取可审计顺序，设置超时并做PG压力样例，不引入分布式解法。
- 公开邮箱存在性侧信道 → 响应一致、邮箱抑制一致、失败密码走dummy hash，避免同步SMTP差异；不宣称形式化恒时网络。
- 未实现功能与授权facts混淆 → 只标记本切片测试，真实媒体/消息/交易场景以后各自验收。

## Migration Plan

先审阅本规划和静态验证，再显式开始apply。协调者先提交根契约与文档供三端同步；端侧代码在各自worktree落地。迁移分身份、会话、关系三步，真正SQL及版本锁定在实施任务中完成。无历史数据迁移；不得自动推送远端或提升main。完成本切片证据后再细化视频和消息；订单/库存/支付/退款/费用/分佣/结算必须联合设计后才编码。

## Open Questions

业务阻塞项已解决；部署SMTP地址/凭据、运行机资源和可用端口在实施配置时提供，不写入仓库。依赖补丁/digest及密码哈希运行耗时须实施时核验，当前不虚构已测兼容版本。初始参数均在工程文档明确，可配置而不改变权限语义。
