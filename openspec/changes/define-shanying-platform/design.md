# Design

## Context

见 proposal.md 与七个能力规格。用户逐轮确认了多商家交易、创作者仅佣金收入、商家自有广告、私密账号及消息权限；这些决定替代初始化草案的功能范围。旧仓库只用于发现细节，不能作为架构、测试或行为正确性的证明。当前没有业务实现，本轮仅形成规划。

## Goals / Non-Goals

Goals：单机可维护的完整业务闭环；Go/React/Kotlin 共享契约；资金依据可追溯；权限在所有入口一致；模拟渠道验证后可扩展真实渠道。

Non-Goals：K8s、微服务、RPC 拆分、分布式数据库/锁/队列、竞价排名、多客服、群聊和音视频通话、复杂优惠促销、真实提现和税务申报。真实微信/支付宝与物流接入另行验证，不把模拟渠道成功称为真实支付验收。

## Decisions

### 1. 单机模块化单体

Go + Hertz 同一后端划分身份/关系、内容、发现、消息、商品订单、资金、广告和管理模块。PostgreSQL 作为业务与持久任务存储；单机后台任务调用 FFmpeg。Docker Compose 管理后端、PostgreSQL、媒体访问及必要单机任务运行环境；不引入 Kitex、K8s 或独立推荐微服务。

保持 Windows 11 开发、Ubuntu 26.04 LTS 运行的已定基线。PostgreSQL 17 为现有工程版本基线，具体镜像补丁版本在实施时锁定。单机不是无并发：库存、预算、消息去重和资金事件使用数据库事务、约束及明确状态转换保证一致性。任务持久化、有限重试、超时恢复，不用内存任务替代可靠状态。

### 2. 三端契约先行

沿用 contracts/ 和 docs/api/、develop 与三端 worktree 流程，以及 bootstrap 中 cross-client-api-consistency 规格。每个业务切片先定义请求/响应/错误/幂等/样例，再实现。Android UI 可较慢，但 DTO、请求、错误和弱网恢复消费测试不得延期到最后。

### 3. 统一权限判定

服务端在请求时检查账号状态、作品可见范围和关系，客户端隐藏仅为体验优化。私密账号公开设置的作品仍需批准粉丝访问；好友作品同时需要互关；仅自己作品仅作者可访问。公开推荐、公开视频搜索和广告只使用公开账号的公开作品。关注流可展示已获授权的私密作品。

媒体访问也必须经权限校验，不能让 Nginx 的永久静态 URL 绕过权限。设计为后端授权后内部转发读取非公开目录；公开媒体缓存需有权限变化后的失效策略。作品权限收紧停止后续未授权请求，不承诺远程擦除用户已下载副本。

消息按“拉黑拒绝 → 客服例外/互关/已有双向会话 → 当前账号隐私及粉丝资格 → 首条额度”判断。客服只豁免陌生人首条限制，不豁免拉黑；售后通过订单/平台入口继续。单方历史不成为双向会话；删除聊天展示也不能重置首条额度。卡片引用不复制访问权。

### 4. 推荐、搜索及媒体

第一版推荐以分类/标签和用户行为统计为基础，候选包含兴趣、近期热门和新内容探索，排序后做权限过滤、去重及作者多样性控制。观看时长与完播率共同使用，曝光与预加载分开，记录推荐请求及反馈以供评估。不先引入模型训练或 Gorse。商品推荐优先当前视频关联商品，再结合用户兴趣。

PostgreSQL 完成用户、视频、商品和店铺搜索；中文分词与短关键词以真实中文样例验证，不宣称默认全文检索足够。初期选择兼容的文本检索/索引方案，避免单独搜索集群。

媒体采用 FFmpeg 异步校验、转码、封面和状态更新；主播放版本 H.264/AAC MP4、faststart、Range 支持，最高 720p 是待样本验证的初始参数，不放大低分辨率。处理旋转和无音轨输入，限制大小、时长、并发和执行时间。本机挂载媒体目录，PostgreSQL 保存元数据，Nginx 受控读文件；不先引入对象存储。HLS/多码率依据首帧、卡顿及带宽实测再决定。

### 5. 订单、归因与精确金额

商品按 SKU 管库存，结算按店铺拆子订单；归因绑定本次购买路径的订单商品，不能用用户最近点击的全局属性污染商城购买。服务端验证来源并保存来源视频/链接、创作者及商家关系，客户端传入 creator ID 不是可信归因依据。商家自己的商品不计佣金。

金额用最小货币单位整数或精确 decimal，禁止二进制浮点。商品实付不含运费作为平台费和佣金各自基数；费用都由商家承担。运费独立列示；固定运费、费率和计费规则版本进入快照。费率需合法且组合不能导致负商品净收入。舍入策略在接口设计阶段固定并给出样例；部分退款按累计应冲减差额计算，最后一次消除尾差。平台收入/商家收入/创作者收入可与支付退款对账。

### 6. 模拟渠道与状态机

订单、支付、退款、物流和结算各自有状态，不能用一个 paid 布尔值覆盖全流程。支付适配统一创建、查询、关闭、退款和通知；模拟适配支持重复、延迟、失败及关闭后成功事件，后端校验后幂等推进。订单超时后迟到成功不自动复活履约，进入退款/异常处理。外部渠道网络调用不置于长数据库事务内；状态与任务先可靠保存，失败后查询/重试。

确认收货后进入售后期，售后中冻结关联金额，满足条件后模拟结算。部分退款按商品/数量/金额关联原交易；退货库存按实际验收结果处理，不因发起退款就自动回补。真实支付接入前另设渠道验签、对账、退款及上线验收，不在当前模拟阶段宣称已完成。

### 7. 不可变资金依据

原始订单商品和费用快照不可因费率修改、内容删除或身份变化而改写。支付、退款、服务费、佣金、广告费、结算及调整具有唯一业务关联与去重键。纠错追加记录，保留原因、操作者及时间，已结算金额的后续调整不能假称已追回。

资金依据不随业务实体软删/注销级联删除；备份、恢复及对账验证属于交付要求。持久保存必要交易证据不等于无限保留全部个人信息；采用最小必要字段及权限控制。真实经营的法定期限、开票、税务与申报规则需接入前专门核实，本规划不作法律结论。

### 8. 广告与治理

商家只投自有公开带货视频，创作者自然流量成交获佣，无额外创作费或广告分成。投放审核后按固定配置计费，不竞价；曝光身份、去重、预算预占/扣减及频次在服务端校验，不能信任任意客户端计费上报。预算与在途曝光共同控制，保证不超支。广告费用规则留快照，转私密/作品限权/商品下架使新增投放停止。

管理后台纳入 React 工程，商家经营和平台管理采用后端权限分离。审核/封禁/退款裁定须留操作依据，不能直接修改数据库最终余额绕过业务账。

## Risks / Trade-offs

- 单机资源竞争 → 转码并发和超时限制；真实样本测试；不以扩展成分布式作为本轮解法。
- 私密资源泄漏 → 统一授权及媒体访问控制；直接 URL、缓存、搜索和卡片负向测试。
- 资金重复或尾差 → 幂等约束、精确金额、累计部分退款与对账测试。
- 模拟结果被误当生产就绪 → 显示模拟属性，真实支付/税务单独验收。
- 功能范围较广 → 按 tasks 的业务切片推进，每组同交契约、测试与说明，未完成项不勾选。

## Migration Plan

先校验本规划并修订旧范围文档，再按任务组建立契约和单机工程。旧仓库按需固定 commit 阅读细节，移植前检查许可证及行为测试，不整仓继承。数据库迁移记录版本，回退不得删除财务依据；通过兼容修复或补偿记录处理已发生业务。依次验证账号/内容、消息、购买、资金、广告、治理，再进行整链模拟验收。未完成前不提升 main 为产品稳定版，不自动发布远端。

## Open Questions

以下为不改变已定业务边界的实施参数，相关任务开始前确定并保存配置/样例：服务费及佣金测试值、广告单价/可见播放阈值/频控、售后期和订单超时、媒体大小时长与并发、邮箱投递环境、金额舍入策略和初始性能目标。未知值不硬写为用户已确认数值。
